# 阶段 1（底层）实施计划（修订版）

## 范围与流程
实现 viewmodels → utils → constants → data 四块。**每块完成即停，报要点待你审查，通过再进下一块**。老项目仅参照（算法语义照搬、代码不照抄），全程只读。

## 表设计（8 张全建，含必要性论证）
| 表 | 必要性 |
|---|---|
| activities / time_entries / activity_categories(+parent_id) / activity_category_links / profile_settings / action_logs | 核心业务/层级分类/设置/操作日志，均必需 |
| app_metadata(key-value) | **必需**：承载 device_id、同步游标、忽略更新版本——技术选型表无 shared_preferences，这些持久化统一落此表 |
| sync_peers | 非阶段 1 业务必需，但建表成本极低，避免阶段 2 加表迁移 |

**不建**（理由见审查）：undo 快照表（内存实现，阶段 3 定）、AI 总结缓存表（二期）、归档表（保留期清理阶段 2 决策）。

## 关键设计约束
1. **deleted_at（可空 text，UTC ISO8601）替代 is_deleted 布尔位**；所有表带 updated_at
2. **软删体系下 FK 不用 ON DELETE CASCADE**（删除是 UPDATE 非 DELETE，物理级联会破坏"删除永远赢"）；递归级联=事务内手动软删
3. 时间列 text 存 UTC ISO8601（TypeConverter<DateTime,String>，字典序=时间序，与同步协议同格式）
4. 部分索引只索引未删行（deleted_at is null）
5. onConfigure：foreign_keys=ON、WAL、synchronous=NORMAL、cache_size、temp_store=MEMORY（出错不阻塞启动）
6. 数据库打开用 drift_flutter 的 driftDatabase（自动处理 Windows/Android 原生初始化，风险#9）
7. 分类写路径集中收口（供阶段 3 dataRevision 挂钩，风险#11）

## 模块 4：data/（drift 单一 schema + 仓储）
### 4.1 schema（app_database.dart + 生成物入库）
- 8 表一次建齐；MigrationStrategy 版本 1（首建无历史迁移）；`dart run build_runner build --delete-conflicting-outputs`，**.g.dart 入库**；先跑通生成再写仓储（drift 首次配置是主要风险点）
### 4.2 仓储（data/repositories/，统一返回 AppResult）
1. activity_repository：CRUD+软删、ensureUnassignedActivity（未分配单例）、softDeleteOneOffActivityIfNeeded、entryWithActivitySnapshot、seed 默认活动（工作/学习/通勤/休息）、LWW replaceIfRemoteNewer
2. category_repository：CRUD、**删除分类事务内递归级联软删（WITH RECURSIVE 查子孙 → 软删子孙分类+各自 links+自身 links，返回被删集合供 undo 作一条记录）**、**parentId 环检测**（禁止挂到自身子孙下）、setActivityCategories（uuid v5 稳定 link id）、LWW
3. time_entry_repository（核心，拆 mixin 保持可读）：跨日拆分（存储时按本地日切段）、重叠裁剪（区间减法，含运行中条目无限区间）、跨日滚转、相邻未分配合并（连续判定+note 换行去重）、switch/stop/split/merge/delete/manual、查询（running/day/range/since/byId）、LWW
4. settings_repository：ProfileSettings 单例读写
5. action_log_repository：写入+查询
- 测试（drift 内存库 NativeDatabase.memory）：跨日多段、重叠裁剪含运行中、滚转、**递归级联软删（子孙+links 全删、单条 undo 数据）**、未分配合并、软删不复活、LWW 并发不复活、环检测、缺键容错
